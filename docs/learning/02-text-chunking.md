# 学习 02：纯文本标准化与切分

## 我们现在处于哪里

工程基线已经完成。现在开始第二个里程碑“最小 RAG 闭环”，当前只处理少量、可控的纯文本：

```text
原始文本 -> 标准化 -> 文本块（chunk） -> Embedding -> 向量数据库 -> 检索 -> 回答
                 ^
                 当前步骤
```

这一版不会调用大模型，也不会写入数据库。`POST /documents/preview` 只展示一段文本经过处理后会变成什么，让切分行为可以先被理解和验证。

## 为什么不能直接保存整篇文档

Embedding 模型通常有输入长度限制。即使整篇内容能够放入模型，一个向量也很难同时准确表达文章中的多个主题。RAG 因此通常先把文档切成较小的文本块，再为每个文本块生成向量。

切得过大，检索结果会混入太多无关内容；切得过小，又可能丢失上下文。不存在适合所有数据的固定答案，切分参数需要通过真实数据和检索评估逐步调整。

## 本次实现

### 文本标准化

连续的空格、换行和制表符会被合并为一个空格。这样，同一内容不会仅仅因为排版不同而产生不同的文档 ID。

当前做法也会丢失段落结构，所以它只适合作为第一版。接入论文、PDF 或 PPT 时，需要保留标题、段落、页码等结构信息。

### 稳定 ID

文档 ID 由来源、标题和标准化文本共同计算；文本块 ID 由文档 ID 和字符位置计算。同样的输入会得到同样的 ID，未来可用于去重和增量更新。

### 正文与元数据分层

每个预览文本块将正文放在 `content` 中，将来源、顺序和字符位置放在独立的 `metadata` 对象中：

```json
{
  "id": "chunk_...",
  "content": "一段文本",
  "metadata": {
    "document_id": "doc_...",
    "title": "RAG 入门",
    "source": "manual://rag-intro",
    "chunk_index": 0,
    "start_char": 0,
    "end_char": 5
  }
}
```

这种分层接近向量数据库中“向量加结构化 payload/metadata”的存储方式。正文用于生成向量和回答，元数据用于过滤、排序、定位和引用。

### 固定字符窗口和重叠

- `chunk_size_chars`：每个文本块最多包含多少个字符。
- `chunk_overlap_chars`：相邻文本块重复多少个字符。
- `start_char` / `end_char`：文本块在标准化文本中的位置。

重叠用于保留切分边界附近的上下文，但会增加向量数量、存储量和计算成本。重叠必须小于块大小，否则窗口不能向前移动。

字符切分容易观察和测试，但可能切断词语。后续可以比较按句子、段落或模型 Token 切分的效果。

## 亲手验证

1. 在项目目录启动服务：

   ```powershell
   uv run uvicorn ai_learning_rag.main:app --reload
   ```

2. 打开 <http://127.0.0.1:8000/docs>。
3. 展开 `POST /documents/preview`，点击 **Try it out**。
4. 输入：

   ```json
   {
     "title": "RAG 入门",
     "source": "manual://rag-intro",
     "text": "RAG 先检索相关资料，再根据资料生成回答。切分决定了检索时能够找到哪些上下文。",
     "chunk_size_chars": 18,
     "chunk_overlap_chars": 4
   }
   ```

5. 点击 **Execute**，观察 `normalized_text`、`chunk_count`、每个块的文字和字符位置。
6. 把块大小分别改成 `12` 和 `30`，比较块数量和上下文完整度。

## 本节验收标准

- 空白格式能够被稳定标准化。
- 相同输入产生相同文档 ID。
- 每个文本块都能追溯到文档和字符位置。
- 文本块正文与结构化元数据保持分层。
- 无效的块大小或重叠参数会被明确拒绝，并返回可理解的失败原因。
- 自动化测试通过，并由用户完成上述接口实验。

当前状态：实现、自动化验证和接口人工验证均已通过（2026-10-01）。
