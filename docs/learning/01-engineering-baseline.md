# 学习 01：工程基线

## 我们现在处于哪里

完整的 RAG 系统会经历数据导入、解析、切分、向量化、检索、重排和答案生成。我们暂时不进入这些环节，而是先建立承载它们的工程基线。

可以把它理解为盖房子前的地基：地基本身不是最终功能，但它让后续每一步都能够运行、验证和安全修改。

## 本阶段解决什么问题

- 不同电脑上的 Python 和依赖版本不一致，导致“我的电脑能运行”。
- 修改代码后，不知道原有功能是否被破坏。
- 项目变大后，文件随意放置，难以理解和维护。
- PR 依赖人工记得运行检查，容易遗漏。

## 本次选择

### Python 3.12

Python 拥有成熟的 AI、文档处理和数据处理生态。项目固定使用 3.12 小版本系列，在兼容现代库的同时，避免不同开发者意外使用不同的 Python 主版本。

### uv

uv 同时负责 Python 版本、虚拟环境、依赖解析和命令运行。关键文件分别是：

- `.python-version`：声明项目默认使用的 Python。
- `pyproject.toml`：声明项目信息、直接依赖和工具配置。
- `uv.lock`：记录完整且精确的依赖版本，使安装结果可复现。
- `.venv`：本机隔离环境，不提交到 Git。

`pyproject.toml` 描述“项目允许使用什么”，锁文件描述“本次确定使用什么”。修改依赖声明后，需要重新生成并提交锁文件。

### FastAPI

FastAPI 用来提供 HTTP API。未来，文档上传、检索和问答都可以逐步成为接口。当前只有 `/health`，它回答一个简单问题：应用是否成功启动并能处理请求？

### pytest

pytest 自动执行测试。第一个测试通过真实 HTTP 测试客户端调用 `/health`，同时验证状态码和响应内容。以后每增加一种重要行为，都应思考其正常路径、边界情况和失败路径如何测试。

### Ruff

Ruff 检查常见代码错误、导入顺序和部分可读性问题。它不能代替代码审查，但能快速拦截机械性问题，让人工更专注于设计和业务逻辑。

### GitHub Actions

CI 会在 PR 和关键分支更新时创建一台干净的临时机器，重新安装锁定依赖并运行 Ruff 和 pytest。它验证的不只是代码本身，也验证项目是否能从零复现。

## 一次请求是怎样流动的

```text
浏览器或测试
    -> GET /health
    -> FastAPI 路由
    -> health() 函数
    -> JSON 响应
```

当前链路很短，正适合学习测试和调试。后续 RAG 问答会在路由之后逐步加入检索、上下文组装和模型生成，但外部接口仍能用相同方式测试。

## 你可以亲手验证

1. 运行 `uv run pytest`，观察测试通过。
2. 将测试中的预期服务名临时改错，再运行测试，阅读失败信息。
3. 恢复测试，运行 `uv run uvicorn ai_learning_rag.main:app --reload`。
4. 在浏览器访问 `/docs`，手动调用 `/health`。

这个小实验的重点是理解：测试失败不是坏事，它是在明确指出“实际行为”和“预期行为”的差异。

## 完成本阶段的判断标准

- 新环境能通过一条命令安装锁定依赖。
- 应用能够启动并返回健康状态。
- 本地代码检查和全部测试通过。
- CI 能在 PR 中重复执行相同检查。
- 初学者能够根据 README 独立完成上述操作。

当前状态：自动验证和人工运行验证均已通过（2026-09-30）。
