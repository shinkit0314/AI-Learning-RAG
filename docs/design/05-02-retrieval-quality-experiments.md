## 5.2.2 · 实验设计

每次提出需要用户确认的判断前，先说明对应的 Issue 编号、`WHAT` 中第几项待办，以及该项待办的相关原文。一个判断涉及多项待办时，先指出主要对应项，再注明前置核对项。

### 决定 1 · 先跑哪组实验（已确认）

基线复跑是两组实验的共同前置。这里讨论复跑通过后，Embedding 和切分哪一组先跑。

| 选项 | 依据与取舍 |
| --- | --- |
| A · 先跑 Embedding | 两处漏掉的证据都已进入原索引，可以先沿用 87 个原片段和人工标注，测试排序是否会变化。需要另一次切分实验来评估片段边界。 |
| B · 先跑切分 | 两处漏掉的证据都有同段的相邻片段被找回，可以优先验证边界是否影响证据覆盖。片段集合变化后，要先复核人工标注，逐题说明相关片段总数的变化。 |

用户已确认 A。先复跑 5.1 基线，再做 Embedding 对照，之后做切分对照。先用同一组片段和标注比较排名，可以减少准备工作，也便于解释变化。两组实验各自与 5.1 的基线比较。若后续发现关键证据在原索引中缺失，或被切散到单条结果无法提供完整解释，可以重新讨论是否优先复查切分。Vespa 的公开教程使用带标注的问题比较检索方法的召回表现。[Vespa 检索召回评测教程](https://docs.vespa.ai/en/learn/tutorials/rag-blueprint.html#evaluating-recall-of-the-retrieval-phase)

### 决定 2 · 第一轮 Embedding 比较什么（已确认）

现有代码把每道问题交给 Qwen 编码时，使用模型自带的查询指令。已核对项目缓存中的固定模型版本，指令面向通用网页搜索。Qwen 官方建议按场景写查询指令，并在多语言检索中使用英文指令。问题正文可以继续使用原语言。[Qwen3-Embedding 官方说明与示例](https://github.com/QwenLM/Qwen3-Embedding#sentence-transformers-usage)

用户确认在同一轮运行三组。原提案是默认指令与 PDF 证据检索指令两组，足以观察任务措辞的影响。加上无指令组后，还能观察加指令本身是否影响检索。

| 组别 | 查询输入 | 用途 |
| --- | --- | --- |
| 对照组 · Qwen 默认指令 | 模型自带指令 `Given a web search query, retrieve relevant passages that answer the query`，后接原问题。 | 保留 5.1 的查询方式，另外两组分别与这一组对照。 |
| 实验组 · PDF 证据检索指令 | `Given a question, retrieve passages from the PDF collection that provide direct evidence to answer it.`，后接原问题。 | 检查强调直接证据是否会改变前五条结果。 |
| 实验组 · 无指令 | 直接将原问题送去编码，前缀为空。 | 观察加上默认指令会不会影响结果。 |

三组使用相同的 Qwen 版本、问题正文、文档向量生成方式、87 个片段、原有人工标注和 Top-5 检索设置。两种有指令的输入沿用相同的格式，各自把同一条指令用于全部问题。三组唯一的主要差异是查询前缀的内容。若未来在独立题集上还有同类排序问题，再考虑用同一组片段和标注比较另一个 Embedding 模型。新模型需要重新生成文档向量，实验成本更高。

### 决定 3 · PDF 切分比较什么（已确认）

两段漏掉的证据都来自被拆成多个片段的长段落。复查 `layout.pdf` 第 3 页的原文块后，确认整段约 1,360 字符，基线切成三片。此前提到的 414 和 514 字符是后两片。把这两片用一个空格拼起来是 929 字符。连同章节路径送入现有 Qwen 分词器计数，得到 158 token。这次只做了计数，实际的切分边界要看候选配置的输出。Azure AI Search 的文档建议考虑段落结构和片段长度，并在编码前检查模型的 token 上限。[Azure AI Search 切分指南](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents)

按 Azure 指南的分类，现有策略最接近 *Variable-sized chunks based on content characteristics*（按内容特征切分为可变长度的片段）。切分器用章节、段落和内容类型决定怎样保留或合并内容。需要拆开长段时，优先选择句末边界，再尝试换行或空白。400 和 600 字符分别是正文切分的目标和上限，实际长度会随内容变化。[Azure AI Search 常见切分方法](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents#common-chunking-techniques)

| 选项 | 依据与取舍 |
| --- | --- |
| A · 把片段最长允许长度从 600 提到 1,000 字符 | 让更多相邻句子有机会留在同一片段。例如第 3 页后两片的文字合起来能通过 512 token 的入库检查，整段约 1,360 字符仍会切分。更长的片段也可能混入干扰内容，或超过项目的 512 token 入库上限。 |
| B · 提高相邻片段的重叠比例 | 可以检查多保留同段附近的上下文是否有帮助。当前实现只重叠满足长度限制的完整短文本块，长段落内部切开的部分无法靠调高这个比例重叠。 |

用户已确认 A。沿用 600 字符上限作为对照，全语料只试 1,000 字符这一个候选值。切分目标长度、重叠比例、PDF、解析和 OCR 结果、5.1 的 Embedding 设置与检索方式保持一致。后续正式检索前先检查各 PDF 的新片段和超出 512 token 未入库的情况，片段集合变化后由用户复核标注。若较长片段反复超限，或独立题集仍出现长段证据被分散的问题，再讨论按 token 上限划分正文。

| 选项 | 依据与取舍 |

### 决定 5 · 切分候选有超限片段时怎么处理（已确认）

现有评分器会校验语料快照和题目集合。基线的入库报告显示，87 个片段已入库，两处被拒均属于当前流程不收录的 `other` 类型，超出 512 token 的片段为零。Azure 的切分指南也强调，编码前应把片段控制在模型输入上限内。[Azure AI Search 切分指南](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents)

| 选项 | 依据与取舍 |
| --- | --- |
| A · 暂停切分候选的正式评分 | 有超限拒绝时先查看被排除的文本。这样可以查清原有证据是否丢失，这一轮可能只交付切分检查报告。 |
| B · 给切分候选中已入库的片段继续计分 | 可以观察放宽上限后的整体结果，包括超限淘汰的代价。需要额外追踪未入库的证据，并说明新标注分母怎样处理这些丢失，复核成本更高。 |

用户已确认 A。若 1,000 字符候选有片段因超过 512 token 被拒绝入库，暂停该组正式评分，记录片段和原文位置，检查有无原本可检索的证据被排除。已经完成的 Embedding 对照可保留。

现有评分器继续按评测集要求检查题目、片段集合和标注。基线复跑的差异处理、候选退步的判断和计时办法留在后续设计中确认。

### 决定 6 · 实验索引存在哪里（已确认）

项目的 PostgreSQL 实现按索引 ID 检索。启用同一逻辑名称下的新索引会停用上一个索引，因此候选需要自己的逻辑名称。#20 需要用 5.1 的原配置复跑。目前逻辑名称也参与索引 ID，改变名称还会改变由索引 ID 派生的记录 ID。现有检索用记录 ID 对完全同分的片段排序。[PostgreSQL 数据库管理概览](https://www.postgresql.org/docs/current/manage-ag-overview.html)

| 选项 | 依据与取舍 |
| --- | --- |
| A · 在现有 PostgreSQL 实例里建一个实验数据库 | 5.1 旧库保留原索引。实验库内的基线可沿用原配置和逻辑索引名，候选各有独立逻辑名称。需要创建一个库并执行现有数据库迁移。 |
| B · 使用当前数据库，为 5.2 各组取独立逻辑名称 | 省去建库和迁移。复跑基线也要改逻辑名称，复核时需要解释新的索引 ID，以及完全同分时可能出现的排名变化。 |

用户已确认 A。只在同一个本地 PostgreSQL 实例增加一个 5.2 实验库，复跑和候选都在该库完成。原库的 5.1 索引与已有报告继续作为验收记录。每组报告写进各自的 `output/` 子目录，档案记录索引 ID、片段集合指纹和使用的配置。当前单机顺序执行，只有以后需要隔离并行实验的数据库负载时，才考虑第二个 PostgreSQL 实例。

### 决定 7 · 怎么判断单题退步和候选改善（已确认）

5.1 基线的 15 道正式题都在第 1 名找到相关片段，14 道在前五条找齐已标注片段。剩下一道有 5 个相关片段，找回其中 3 个。在这一个题上找齐两片，平均 Recall@5 就能提高约 2.67 个百分点。需要查看逐题结果，才能知道这个增幅是否伴随其他题退步。Elasticsearch 的排名评测同时提供汇总分数和逐题报告。[Elasticsearch 排名评测接口](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-rank-eval)

| 选项 | 依据与取舍 |
| --- | --- |
| A · 先守住每题，再判断收益 | 正式题的首条结果都应继续相关，前五条应保留原已找回的答案证据。只要确认有一道题退步，本轮就先保留基线配置。门槛较严，可能暂时保留有局部收益的候选供复查。 |

用户已确认 A。逐题记录首个相关结果的位置，以及前五条新增或丢失的原文证据。Embedding 对照可按原片段身份查差异，遇到内容重叠的片段再核对证据是否仍在。切分对照用人工复核的新标注，并按原 PDF 页码、原文块和具体句子判断同一证据是否仍被找回。例如同一证据从两个相关片段合为一个时，只看片段数会误判。现有 Recall@1/3/5 和 MRR@5 继续报告。跨切分设置时，逐题注明相关片段总数和原文证据变化。Chroma 的切分研究也用原文中的相关文本衡量覆盖，本轮题量较小，用人工核对原文即可。[Chroma 切分评测研究](https://www.trychroma.com/research/evaluating-chunking)

### 决定 8 · 怎么测量索引构建成本和检索耗时（已确认）

5.1 的报告保存模型和运行环境信息，但没有保存耗时。首次查询还可能包含 GPU 初始化或数据库连接的开销。PyTorch 的基准测试文档示范了先热身、再重复计时的方法。[PyTorch 基准测试指南](https://docs.pytorch.org/tutorials/recipes/recipes/benchmark.html)

| 选项 | 依据与取舍 |
| --- | --- |
| A · 每组构建记一次，查询热身后计时三遍 | 能用中位数减少单次调度波动的影响，也能看清哪些题更慢。在同一台机器上需要额外跑两遍带计时的查询和一遍热身。 |
| B · 每组构建记一次，查询只计时一遍 | 可以直接给质量评测增加计时。结果容易受单次波动左右，只适合粗略查看耗时。 |

用户已确认 A。使用同一台机器、GPU、Qwen 环境和实验数据库，按相同题序串行执行。

- **索引构建**。从开始生成文档向量到写完并启用索引，记一次耗时。记录实际入库片段数和这些向量的存储字节数。数据库共用物理表，向量字节数按本组的行汇总 `pg_column_size(embedding)`。如果某组复用已生成的向量，单独记实际发生的写入成本。[PostgreSQL 存储大小函数](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADMIN-DBSIZE)
- **检索**。模型和索引准备好后，先用同一组 18 道题热身一遍。再按题序跑三遍，从准备问题向量前计时，到数据库返回前五条结果停止。报告记录各题三次耗时的中位数、全组耗时的中位数和范围。第一次计时的查询结果也用于正式质量评分。
- **预算**。每套配置共 72 次查询，四套都完成时共 288 次，包含已经确认的 72 次质量评估查询。在本机记录每套实际用时。若几组耗时差异小于重复测量的波动，结论写明目前无法判断哪组更快。以后只有在耗时确实影响采用决定时，再增加采样。
