# AI-Learning-RAG 项目目标与需求

> 本文档是项目需求的长期基线。新增、修改或废弃需求时，应同步更新需求编号、验收标准和文末的变更记录。

- 已确认基线版本：`0.4`
- 当前修订版本：`0.4`
- 最近确认日期：2026-10-01

## 1. 项目愿景

逐步搭建一个用于学习、沉淀和检索 AI 技术知识的 RAG（Retrieval-Augmented Generation，检索增强生成）系统，并形成可持续扩展的 AI 技术知识库。

项目既要产出可运行、可测试、可维护的系统，也要完整呈现 RAG 系统从设计到落地的知识、技术选择、实验过程和常见难点，帮助初学者逐步掌握 RAG 技术。

## 2. 目标用户与设计原则

### 2.1 目标用户

- 正在系统学习 AI 和 RAG 技术的初学者。
- 希望通过真实项目理解数据处理、检索、生成、评估和工程化流程的开发者。

### 2.2 设计原则

- **循序渐进**：每个阶段只引入必要的新概念，先建立最小可运行闭环，再逐步增强。
- **学习优先**：说明关键概念、设计理由、替代方案、技术取舍和常见陷阱。
- **实践驱动**：每项核心能力都应配有可执行示例、测试或实验。
- **质量内建**：功能开发与测试同步进行，避免测试长期滞后于实现。
- **保持简洁**：优先采用清晰、可读、易维护的实现，避免不必要的抽象和复杂度。
- **举一反三**：在完成当前任务的同时，指出可迁移到其他 RAG 场景的思路和边界。

## 5. 工程质量要求

### 5.1 测试要求

- `QUAL-001`：测试用例必须随功能持续补充和迭代。
- `QUAL-002`：每一个 PR 都必须通过当时约定的全部自动化测试。
- `QUAL-003`：修复缺陷时，原则上先增加能够复现问题的回归测试，再修复实现。
- `QUAL-004`：测试应根据风险逐步覆盖单元测试、集成测试、端到端测试和 RAG 效果评估。
- `QUAL-005`：涉及模型输出的测试应避免只依赖完全一致的自然语言字符串；优先验证结构、引用、关键事实和可量化指标。
- `QUAL-006`：任何测试失败都不得通过删除、跳过或弱化有效断言来掩盖，除非在 PR 中说明原因并经人工确认。

### 5.2 代码质量要求

- `QUAL-007`：代码应命名清晰、职责单一、结构易读，并保持必要而不过量的注释。
- `QUAL-008`：公共接口、重要配置和复杂逻辑应有文档或示例。
- `QUAL-009`：提交内容应聚焦当前目标，避免混入无关重构或格式化变更。
- `QUAL-010`：密钥、令牌及敏感数据不得提交到仓库。
- `QUAL-011`：依赖和配置变更应说明用途、影响与必要性。

## 6. PR 与人工确认流程

每次迭代遵循以下流程：

1. 明确本次学习目标、功能范围和验收标准。
2. 先检查现有实现和测试，再进行小步修改。
3. 新增或更新与改动匹配的测试用例。
4. 在本地运行相关测试；提交 PR 前运行约定的完整测试集。
5. 在 PR 中说明：做了什么、为什么这样设计、如何验证、已知限制以及建议的人工检查项。
6. 自动化测试全部通过后，等待人工确认。
7. 未经人工确认，不将本次迭代视为最终验收完成。

### 6.1 PR 完成定义（Definition of Done）

一个 PR 至少满足以下条件才可进入人工确认：

- 功能与本次验收标准一致。
- 新增或变更行为有相应测试。
- 相关测试和完整测试集均通过。
- 代码、配置和文档保持同步。
- 没有提交敏感信息或无关改动。
- 已记录关键技术选择、局限和后续建议。
- 已列出可由人工复核的操作步骤和预期结果。

## 7. 学习与指导要求

每个开发阶段应尽量包含以下学习内容：

- **本阶段要解决的问题**：它在完整 RAG 链路中的位置和价值。
- **核心概念**：用初学者能够理解的语言解释术语和原理。
- **方案比较**：至少说明所选方案的理由、代价和适用边界。
- **动手实验**：提供可运行的小实验或测试，观察参数变化带来的影响。
- **常见问题**：指出易错点、调试方法和生产环境风险。
- **知识迁移**：说明该思路还能应用到哪些数据源、模型或业务场景。
- **阶段复盘**：总结已经掌握的内容，并给出下一阶段的学习前置知识。

指导过程应耐心、具体，不默认用户已掌握未介绍的概念。遇到重要技术决策时，应先解释选择空间和权衡，再推进实现。

### 7.1 初学者引导与兜底机制

- `LEARN-001`：持续判断用户是否清楚当前进度、下一步目标和执行方法，不能因为用户没有主动提问就默认其已经理解。
- `LEARN-002`：当用户不知道下一步做什么时，先说明“现在处于哪里、接下来要解决什么、为什么值得先做”，帮助用户建立整体方向感。
- `LEARN-003`：优先通过简短问题、可选方向、判断标准和小实验，引导用户自己分析并选择下一步，而不是直接替用户完成所有决策。
- `LEARN-004`：提出选项时，应使用初学者能够理解的语言解释每个选项的收益、代价、难度和适用场景，并明确给出推荐项及推荐理由。
- `LEARN-005`：避免一次提供过多概念或分支。默认给出一个清晰的当前步骤，并说明完成后会自然进入哪一步。
- `LEARN-006`：如果用户仍然无法判断、明确请求代为决定，或继续等待会阻碍项目推进，应选择风险较低、易理解、可逆的方案作为兜底，并明确说明所作假设。
- `LEARN-007`：兜底不是替代学习。完成兜底操作后，应解释做了什么、为何这样选择、用户可以观察什么结果，以及未来如何自行作出同类判断。
- `LEARN-008`：涉及高成本、不可逆、敏感信息、外部发布或项目方向重大变化的决定，不得自行兜底，必须等待用户确认。
- `LEARN-009`：AI 技术专家应负责维护完整、连贯的学习路线，根据 RAG 全生命周期安排项目顺序，不把路线规划责任转嫁给初学者。
- `LEARN-010`：用户提出疑问、假设或不同看法时，应先判断其技术影响并给出有依据的专业结论，不把疑问自动视为改变实现或路线的指令。
- `LEARN-011`：用户参与应聚焦于能促进理解的预测、实验、结果解读、代码阅读和关键权衡；对于超出当前认知阶段的决策，应先给出推荐方案和理由，再提供安全兜底。

推荐采用以下引导顺序：

1. **定位**：说明当前阶段、已完成事项和当前障碍。
2. **启发**：给出一个容易回答的问题或一个最小实验，让用户尝试判断。
3. **提供选择**：给出少量清晰选项、判断标准和推荐方向。
4. **协助执行**：根据用户的选择拆解并完成下一小步。
5. **兜底推进**：用户仍无从选择时，采用推荐方案推进，并解释假设与回退方法。
6. **复盘迁移**：总结本次判断方法，使用户下次能够更独立地找到方向。

## 8. 建议的渐进式里程碑

里程碑的具体技术方案和验收指标将在进入对应阶段前共同确认。

1. **工程基线**：项目结构、开发环境、配置、日志和测试框架。
2. **最小 RAG 闭环**：使用少量纯文本完成导入、切分、索引、检索和回答。
3. **PDF 知识库**：加入真实 PDF 解析、引用定位和解析质量测试。
4. **检索质量提升**：实验切分、嵌入、混合检索、过滤和重排策略。
5. **RAG 评估体系**：建立固定评测集、指标、回归基线和结果报告。
6. **多源数据接入**：逐步支持论文网站、技术博客、PPT 和图片。
7. **可观测与知识库维护**：增加链路追踪、增量更新、去重和版本管理。
8. **应用与部署**：根据学习目标决定是否加入 API、界面、权限和部署能力。

## 9. 需求管理规则

- 每条稳定需求使用唯一编号，已有编号不重复使用。
- 需求状态使用：`待规划`、`进行中`、`已实现`、`已验证`、`已废弃`。
- 新需求应补充目标、动机、验收标准、优先级和依赖关系。
- 修改需求时，应同步更新受影响的代码、测试、文档和里程碑。
- 需求存在歧义或会显著改变项目方向时，应先讨论并获得人工确认。
- 已废弃的需求保留记录和废弃原因，避免后续重复决策。

## 10. 待共同确认的决策

以下内容暂不提前锁定，将在对应里程碑开始前结合学习目标进行选择：

- 主要编程语言和应用框架。
- 大语言模型与嵌入模型（本地或云端）。
- 向量数据库和元数据存储方案。
- 首个正式接入的数据源。
- 评估数据集、质量阈值、性能目标和成本预算。
- 最终交互形式与部署环境。
