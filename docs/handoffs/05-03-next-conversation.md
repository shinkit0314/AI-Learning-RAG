## 5.2 的结论和验证

- 用户已确认 5.3 以 v1.0.0、600 字符切分上限、Qwen 默认查询指令和精确向量检索为对照。
- Embedding 实验中，PDF 专用指令使一道题失去首条相关结果。无指令有一题进入前三、另一题掉出前三，前五证据相同。
- 1,000 字符切分将 87 个片段减到 69 个，向量空间下降约 20.7%。平台题首条结果找齐 12 个平台，系统设计题失去原有的第 3 页证据。保留 v1.1.0 的候选标注和报告，供后续解释切分实验。
- Ruff 格式和静态检查通过，默认 pytest 运行有 303 项通过。用户在独立的 `ai_learning_rag_test` 数据库显式运行 `uv run --locked --no-sync pytest -m postgres_integration`，两项集成测试均通过，覆盖 pgvector 索引写入、重复写入、版本替换、并发冲突及 PDF 检索的页码和原文块追溯。
- 5.1 基线复跑与原 JSON、Markdown 报告字节一致，真实 Qwen/PostgreSQL 已完成三组 Embedding 和两组切分对照。详细证据见 [5.2 设计与验收](../design/05-02-retrieval-quality-experiments.md)。

## 限制与第一步

- 当前评测只有 3 份 PDF、15 道正式题和 3 道诊断题。跨切分设置要对照原文证据和各自的相关片段总数。当地环境的检索中位数差异小于 1 毫秒，原始 600 字符组未测构建时间。
- 5.3 开始时先重新核对 `develop` 和实际的 5.2 验收结论。查清现有索引可以使用哪些元数据，基线问题中哪些确实需要限定范围或兼顾精确术语，再提交一个优先验证的场景给用户确认。混合检索、过滤、查询改写和重排器均未在 5.2 引入。
